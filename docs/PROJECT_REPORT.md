# 从分类结果到可复核记录

## 为什么继续做数字识别

第一版已经能训练、预测和展示图表，但预测一次以后就结束了。如果用户要核对一批图片，还缺少待处理列表、修改记录和最终导出。这次保留模型，把工作重点移到这段流程。

项目借鉴 Label Studio 对预测与标注的区分、FastAPI 官方模板的资源接口，以及 Made-With-ML 的分组评估思路。具体阅读位置记录在调研笔记中，没有把参考仓库改名作为提交物。手写网络、SQLite 和置信度排序也都不是新发明。

## 一张图片如何成为一条记录

导入接口先检查全部文件，再进行推理，最后在事务中建立批次。如果其中一张不能解码，整个批次不写入。上传原图以 Base64 保存在单独的 `originals` 表；列表只读取模型输入，选中图片才读取原图，避免每次分页返回全部原文件。

模型输入经过灰度化、明确选择的颜色反转、可选居中及 BOX 缩放，得到 8×8 像素。原图必须保留，因为缩小后丢掉的笔画可能正是复核需要看的部分。文件 SHA-256 用于批次内去重；同一图像用另一种编码保存仍可能产生不同摘要，这里没有声称实现感知去重。不同原图即使得到相同 8×8 输入，也保留两条记录。

公开测试样本直接来自原始像素数组，没有伪造拍摄原图。它们以输入像素摘要去重。模型加载时核对文件 SHA-256 与训练报告，记录中保存该指纹和预处理选项。

## 为什么纠错不覆盖预测

`prediction` 是模型当时的输出，`final_label` 是复核后的结论。直接覆盖预测会让后续分析无法区分模型表现与人的修改，也容易把纠正后的结果误算成模型准确率。因此界面和导出均保留两者。

状态包括待复核、已确认、已纠正、无法辨认。撤回复核清空最终标签，并增加事件，不删除历史。事件包含前后状态、版本、备注、署名和 UTC 时间。记录署名由使用者填写；本地应用没有账户认证，不能把它当成身份审计系统。

保存采用 SQLite 事务与版本检查。两个页面打开同一版本，只有先保存的操作成功；后保存的返回 409。请求编号和内容摘要用于重试：相同请求返回原结果；相同编号换了内容会被拒绝。当前实现中重复导入请求仍可能先重复推理，但不会建立重复批次，这是后续可以优化的计算开销。

## 复核排序是否值得做

低置信度不等于错误，但可以作为检查顺序。实验固定模型，对 270 张保留测试图以及两种规则扰动分别比较置信度升序和 1000 次随机排列。排序过程不读取标签；统计命中错误时才使用真值。

在原始图上，检查 20 张遇到 3 个错误中的 2 个，随机均值为 0.206。噪声场景为 14 对 2.476，降低亮度场景为 16 对 5.106。完整预算曲线和逐样本记录在 `artifacts/review/`，可以重跑脚本核对。

这个实验有明确局限：测试集在第一版已经看过，结果是回顾性的；扰动分布不是用户图片分布；“遇到错误”不等于人一定能正确修改。特别是 sample 5 的原始预测以约 99.42% 的置信度把 5 判成了 9，说明队列不能代替其他质量检查。没有人工研究，因此没有工时节约或业务收益数字。

## 本次修正中值得留下的经验

检查真实使用流程时，发现两个容易被界面掩盖的问题。其一，只保存预处理像素会让复核者失去原图证据；其二，按时间戳和名称排序不保证导入顺序，因为多条记录可能在同一毫秒写入。这次分别补了原图表和按插入记录顺序读取，并用测试构造“不同原图缩小后相同”及“文件名逆序”的情况验证。

这些是实现中可复查的设计经验，不代表提交者个人已经经历或掌握的内容。提交者可以从中选一个问题，自己修改并重跑测试，再写自己的感悟。

## 验证与尚未覆盖的场景

本次本机测试 23 项通过，包含数据划分、模型与推理、输入校验、重复请求、持久化、并发修改冲突、导出字段和原图保留。测试出现一条 Starlette/AnyIO 的弃用警告，日志保留，没有屏蔽。

实际 Chrome 操作完成载入 270 张、纠正公开样本 555、查看修改记录、刷新恢复、导出、重复图片导入以及实验页检查。浏览器没有捕获到页面脚本异常，390px 宽度检查没有水平溢出。视频和操作时间记录一并保存。这是流程验证，不是多浏览器兼容性或性能压测。

当前适合本机单数字复核。不支持整页检测、多人账户、远程部署权限管理、自动再训练或数据库备份调度。SQLite 保存原图的方式便于小规模交付，但 Base64 会增加体积，长期大批量使用应把原文件移到受控文件存储，并增加保留与清理策略。现阶段没有大规模吞吐量或生产可用性结论。
