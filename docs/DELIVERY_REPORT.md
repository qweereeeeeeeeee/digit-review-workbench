# 图片识别与复核：项目说明与开发复盘

交付日期：2026-11-13。仓库：<https://github.com/qweereeeeeeeeee/digit-review-workbench>。

## 项目做什么

上传照片后，系统给出物体区域和文字、数字的识别结果。使用者对照原图检查，确认或改正结果，再保存和导出。它适合本机演示、整理少量图片和检查模型错误；不能保证识别所有物品，也不是能够自动承担业务判断的生产系统。

项目有两个相互补充的部分。考核基础部分是用 PyTorch 手写并训练的数字 ResNet，包含完整数据分析、训练和评估过程。拓展部分是把成熟的 Florence-2 和 PaddleOCR 模型接入同一个复核流程，让手机照片、文字和多个物体可以在一张图中分别处理。预训练模型不替代手写 ResNet，也不冒充自行训练成果。

## 技术和实现过程

基础数据来自 scikit-learn 提供的 UCI 手写数字数据，共 1797 张 8×8 灰度图。NumPy 负责数组、归一化和指标计算；Pandas 保存并核对数据表、分组统计和逐样本预测；Matplotlib 绘制分布、训练曲线、混淆矩阵及复核队列实验。训练、验证、校准、测试分别为 988、269、270、270 张，划分索引和文件摘要均保留。

`src/model.py` 编写了残差块和三阶段网络。跳跃连接让输入绕过卷积分支，再与分支结果相加；尺寸变化时用 1×1 卷积匹配。网络有 174970 个参数，实际训练 40 轮，按验证交叉熵选中第 22 轮权重。基础模型没有调用预训练 ResNet 来代替手写网络。

原 270 张保留测试图中，模型识别正确 267 张，即 98.89%。这个数字只说明指定 UCI 划分上的结果，不代表手机拍摄手写照片的准确率。训练记录、模型、逐张预测和三个错误样本都在 `artifacts/run-001/`。本次打包再次从权重重算这 270 张预测，并核对报告与 CSV。

真实照片暴露了原方案的局限：一张有阴影、纸张和多位数字的照片，被整体缩成 8×8 后会丢失重要笔画。后来接入 YOLO11s 的 COCO 权重虽然能找常见物体，但固定 80 类既不包含火箭，也不负责读文字。这个问题来自模型任务和输入分布，不是换一个漂亮界面就能解决。

新版采用 Microsoft Florence-2-base-ft 生成区域描述，PaddleOCR PP-OCRv5 server 经 RapidOCR 和 ONNX Runtime 定位并识别文字。二者都处理完整原图，可选局部框选。实际比较过 EasyOCR、PP-OCRv4 和 Florence 自带 OCR，最终采用 PPv5。模型来源、固定版本、SHA-256 和下载方式均在清单中，启动时逐文件校验。

后端使用 FastAPI 接收图片并返回结果，SQLite 保存原图、模型输出和复核记录。确认结果与原预测分开存储，避免人工改对以后被误统计为模型正确。重复请求通过请求编号返回原回执；同一条记录的过期修改会得到 409 冲突。图片大小、格式、坐标和数字范围都有校验。界面通过编号把结果与图中的区域对应起来。

## 已得到的结果和仍然存在的问题

此前上传的四张完整手写照片分别读到 `7`、`114514.`、`8`，以及 `N=` 和 `6`。最后一张主要数字虽已读出，背景仍被额外识别。物体描述模型还曾把数字 8 描述为字母 B；界面保留两条分支的原始分歧。

公开火箭照片能够定位到火箭。宇航员照片返回人物、旗帜、头盔、人脸区域，但人脸属于人物的一部分，不能简单按区域数计算独立物体数。咖啡图把同一把勺子框了两次；猫图有 `op` 的 OCR 误报；摄影者图把人、相机和三脚架合在一个框中。这些情况在验证报告中逐项列出，没有删除失败图。

上述照片已参与开发选型，不是独立测试集，项目没有据此计算“通用准确率”。新模型在这台 Intel Mac 上通常需要十几到几十秒处理一张图，记录中保留每次实际耗时。服务只用于本机，尚未验证高并发、远程账户权限或长期大规模存储。

## 拓展点与开发难点

项目的拓展重点是把预测做成可检查的过程：同时保留原图、区域坐标、原始输出、模型文件摘要和人工修改记录；数字、物体使用适合各自任务的成熟模型；不把不同模型的分数平均成一个虚假的高置信度。Florence 没有提供校准概率，因此不为区域结果显示伪造百分比。

基础版还比较了固定检查预算下的低置信度排序和随机检查，保留全部预算曲线与逐样本结果。它只能说明这批样本上先看哪些图片更容易碰到错误，没有测量真实人工工时，也没有宣称业务效率提升。

难点首先是识别模型是否适合真实输入，其次是 CPU 环境下的版本兼容和速度，再次是纠错后的数据是否还能追溯。工程处理包括固定依赖与模型版本、保留失败基线、分别记录各模型输出、验证裁剪坐标还原以及处理复核版本冲突。这些属于已有方法的工程组合，不宣称原创识别算法。

## 个人感悟：来自这次真实测试的反馈

这一节依据提交者在本次测试中明确提出的反馈整理，不虚构其独立编码或掌握全部技术的经历。

“不能只在测试集上表现好”是这次最重要的要求。最开始能展示训练图表和测试分数，但亲自拍摄的手写数字识别失败，说明展示数据和实际使用之间有很大距离。把这些失败留下来，比重新挑几张能识别的图更有价值。

第二个体会是要先判断工具是否适合问题。数字分类器不负责识别火箭，固定类别的物体检测器也不等于 OCR。参考成熟项目有帮助，但需要真正安装、运行和比较；调用开源模型之后，仍然要处理输入、记录、界面和错误。项目的改进正是由这些现场问题推动的。

第三个体会是 AI 辅助和本人理解是两回事。当前项目使用了 AI 辅助编程和文档整理；答辩时仍需要本人解释残差连接、训练与推理的区别、原预测与人工结果为何分开，以及如何重现一个失败样本。随包的 `docs/DEFENSE.md` 提供练习问题，不能将自动测试通过当成已经掌握代码的证明。

## 来源、许可与运行方式

参考来源包括 Microsoft Florence-2、Autodistill Florence-2、PaddleOCR、RapidOCR、EasyOCR、Ultralytics、torchvision，以及早期复核流程参考项目。具体链接和读过的代码位置见 `docs/research/`；不是将某个参考仓库整体改名提交。模型、上游代码与本地组件各自的许可分别保留，不混为“全部原创”。

Python 3.12 环境中安装 `requirements.txt`，模型文件齐全后运行 `sh scripts/start_objects.sh`，打开 <http://127.0.0.1:8768/>。基础数字版运行 `sh scripts/start.sh`，打开 <http://127.0.0.1:8766/>。完整包带模型文件，精简包通过两个模型下载脚本获取官方权重；两者都需要安装 Python 依赖。macOS 自动启动方式见 `docs/LOCAL_SERVICE.md`。

仓库保留实际开发提交，交付包另附本地 Git bundle 和远程提交快照。最初阶段只有本地历史，之后才开始远程分阶段提交；不补造过去的远程上传记录。普通打包文件不包含日常数据库、私有上传照片、缓存和本机虚拟环境。
